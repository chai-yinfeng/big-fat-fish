# Authority memory boundary v2 (0.9 content extension; database schema unchanged)

Authority is the independent canonical service. It has no DSH Session, browser, platform SDK or provider dependency. QQ and the console are channel adapters, not separate personalities. One SQLite writer may manage multiple isolated companion entities.

## Identity and ownership

- `entityId` identifies a controlled personality and its own memory/relationships. `DEFAULT_ENTITY_ID='entity:big-fat-fish'` preserves the existing world. `personId` identifies a real interaction partner, not a companion personality. A conversation/session is neither of those.
- Operator binding `(capabilityId,streamId) -> {entityId,personId,audience:'private'|'shared'}` determines the scope. Multiple streams may bind one entity/person. Model requests cannot pass an arbitrary entity or person selector. Changing an existing binding in place is refused; a new explicit conversation binding is needed.
- `(capabilityId,externalActorId) -> personId` remains operator-confirmed. Message text cannot establish identity. Capability credential identity is not human identity.
- Admin alone creates entities, changes persona, authorizes public material, pins/sets event dates, publishes diary drafts or forgets content. Ordinary model proposals cannot alter these permissions.

## Storage and migration

Node 24 `node:sqlite`, DELETE journal, `locking_mode=EXCLUSIVE`, FULL synchronous, foreign keys and `secure_delete=ON`. The writer retains its SQLite lease until close; the kernel releases it on process death. No new dependency, WAL conversion or secondary memory writer. Schema changes after v2 are additive migrations (`src/migrations.js`): applied at open in one transaction, recorded in `schema_migrations`, preceded by a `VACUUM INTO` backup of an existing database in `migration-backups/` beside it. `user_version` stays 2; none is registered yet.

Opening a valid v1 database performs an atomic transaction to v2: legacy memory arrays become individual `memory_items` with incremental local Chinese/Latin `memory_tokens`, provenance links and entity IDs; persona/relationships move into entity-scoped rows. Observations, proposal inbox, receipts, audit and identity bindings are preserved. Existing persona revision and the entire world pause/clock record are preserved, never bootstrapped/reset. Failure rolls back DDL, rows and `user_version` together. Application ID remains unchanged. Config `schemaVersion:1` is separate from SQLite `user_version:2`.

Only the small global world clock remains in metadata state. Production context/review reads and updates bounded candidate/item rows, not the old global JSON corpus. Admin `snapshot()` retains the old default-entity `facts/notes/experiences/appraisals` fields for compatibility; other entities require explicit entity selection/listing. Snapshot is never a capability endpoint.

## Evidence and ordinary memory proposals

Existing closed proposal DTOs remain:

- `fact.report {key,value,quote}`: confirmed user, private bound stream. `value` is the fact as the companion understood it (a relative date resolved, a wording normalised); it need not occur in `quote`. An attributed report, not semantic fact verification. A new report supersedes the active fact for the same entity/person/key, retaining the old record and its source but excluding it from ordinary retrieval.
- `experience.remember {summary,quote}`: evidence-bearing conversational experience.
- `learning.note {text,quote}`: external reading source, entity-owned private knowledge, never a human preference/intimacy declaration.
- `self.note {text,quote,kind:'outer'|'inner'}`: private conversational notes. `outer` does not mean public. Inner never enters a conversation capability.
- `appraisal.record {kind,quote}`: trusted enum/delta, once per source observation, entity/person-scoped relationship.
- `persona.change`: always rejected for capabilities; explicit operator persona revision remains separate.

Provenance is the observation, not the quote. Every accepted item records `evidence {observationId,quote,role,actorId,streamId,at}` for the observation the proposal cites, which must exist and belong to this person's private conversation; ownership, visibility and the forget cascade follow that observation. `quote` is required and stored as submitted, but is no longer a gate: when it does not occur in the observation's text (compared after NFKC folding, ignoring punctuation, symbols and whitespace) the item is still accepted and carries `evidence.quoteVerbatim:false`. The key is absent on a verbatim quote and on every item written before this rule, so stored bodies are unchanged and an older release ignores it. `review()` no longer returns `quote_not_in_observation` or `value_not_in_quote`; it still returns `private_binding_required`, `sensitive_retention_denied`, `sensitive_source` (the cited observation's own text matches the same sensitive guard, whatever the proposal would store), `unconfirmed_identity`, `real_user_required`, `conversation_role_required`, `conversation_policy_kind_denied`, `authored_text_required`, `observation_already_appraised` and the learning-policy reasons. Operator `GET /memory` shows the mark with the item's evidence, and `GET /memory/sources` returns the cited observation for comparison.

Quote substring, trusted role, person/entity scope and conservative sensitive-content checks are deterministic. They are not a second model or semantic truth classifier. Proposals first enter the durable inbox; only the serial server reviewer applies effects/receipt/non-content audit atomically. A pending receipt is not a remembered fact. Paused proposals reject, and pre-pause pending work waits for resume.

Raw observations and rejected proposals remain private evidence until explicit forgetting; declining retention is not deletion. Unbound observations cannot confer a different entity's permissions when a binding later changes.

## Capability API (UDS bearer, no operator credential)

`AuthorityClient` uses fixed routes, bounded JSON and generic errors; no arbitrary HTTP/admin operation.

- `observe({eventId,streamId,actorId,role,text,at,origin?})`, `submit({proposalId,observationId,type,payload})`, `getReceipt(id)` retain the original semantics. Forgotten event replay returns `{observationId,duplicate:true,forgotten:true}` without retaining the supplied text. New proposals referencing an erased source are refused.
- `context({streamId,query?,budgetChars?,exclude?,profile?,windowFromAt?})` -> `{revision,entityId,memoryEpoch,personaRevision,text,personaText,memoryText,memoryIds,profileText,scope,world}`. `memoryIds` are the entries rendered into `memoryText`; `exclude` (at most 256 memory IDs) are never retrieved, so a caller that keeps earlier results in front of the model does not get them twice. `profile:true` also returns `profileText`, the standing profile of the person in a private `conversation.v1` chat (their pinned facts first, then facts by importance, newest first; whole lines within 1000 characters, outside `budgetChars`, independent of the query; `''` otherwise); its entries are not retrieved into `memoryText`. `text` is the whole rendered context; `personaText` and `memoryText` are the same content apart (`text` = `personaText`, a blank line, `memoryText`), so an executor can keep the persona in a stable system prompt and attach the per-query memory separately. Default budget 4000 characters; class API maximum 16000, restricted client maximum 4000. The persona has its own budget of 2400 characters (60% of a smaller `budgetChars`), the same with or without memories, and is cut at its end beyond that; memory groups share the rest fairly, but retrieved memory is always capped at the 6 best-ranked entries and 900 characters, whatever the budget; an entry the cap leaves out is not in `memoryIds` and can be retrieved by a later call. Evidence-bearing lines are atomic. A memory line is quoted JSON `{content,date}`: the attributed content and the UTC day it was recorded; the evidence quote, observation/actor/stream IDs, role and policy are not rendered into context (they stay available to memory tools and the operator). SDK history/tool schemas/metadata have their own budgets and are not included in this character cap.
- `windowFromAt` (ms) is the executor's report of when the oldest run it still replays for this conversation began. Authority keeps the newest value per private `conversation.v1` stream in memory (not in the database; after a restart it is unknown until the next run) and uses it only to tell which dialogue has left the window (see Consolidation). It changes nothing in the response.
- `memorySearch({streamId,query,limit?:8,budgetChars?:2400})` via POST `/v1/memory/search` -> `{entityId,memoryEpoch,items:[{id,type,excerpt,importance,pinned,revision}],text,world}`. Limit maximum 32.
- `memoryRead({streamId,id})` via POST `/v1/memory/read` -> `{entityId,memoryEpoch,item|null}`. ID lookup still enforces the current stream's entity/person/audience. It cannot read private diaries, inner notes, machine digests or superseded entries.
- `memoryRecall({streamId,fromAt,toAt,limit?:8,budgetChars?:2400})` via POST `/v1/memory/recall` returns only authorized candidates (pinned items, facts with importance >= 0.8, experiences with importance >= 0.65, their default) with `{id,text,recordedAt,eventAt,dateBasis,importance,pinned}` and `isNewEvidence:false`. Limit maximum 16. This is a query, not an automatic anniversary scheduler or a newly happened experience.

- `admitPerson({uid,actorId,streamId})` via POST `/v1/people/admit`: only for a conversation capability whose channel declares a friend relation (`capabilities/channels`; 403 otherwise). The bridge names the account (`uid`, in the shape the channel declared) and, in the channel's own terms, its actor and private conversation; Authority holds both IDs to the channel's namespace (they start with `<capabilityId>:`, are plain `[A-Za-z0-9:._-]` and at most 128 characters) and binds them to one person. A new person is named `person:<capabilityId>:<uid>`; that name is opaque and no code reads meaning from it. The entity comes from the owner's binding on that channel (409 until the owner is bound there). Idempotent (`{personId,streamId,admitted}`), at most 40 admitted people counted as distinct people over all channels (409 `PEOPLE_LIMIT`), audited as `person.admit`. Whether the account is a friend is the bridge's decision, the same trust boundary as actor IDs. The owner stays `person:owner`. QQ sends actor `qq:<self>:user:<uid>` and stream `qq:<self>:private:<uid>`.
- `context` also returns `capabilityId`: the channel the conversation is on (the caller's own capability). The executor picks the channel's fixed part of the system message by it.
- Identity and memory: a person is whoever actors are bound to (`actors`: capability + actor -> person); a conversation (`streams`) is bound to one person on one channel. Facts, the standing profile, digests and relationships belong to the person and are the same on every channel that person has an account on; observations, the replay window, the consolidation cursor and the memory epoch belong to the conversation. A capability credential reaches only the conversations of its own capability.
- Model-facing output never contains raw person IDs or the word "owner": reported facts render as `Reported by p-xxxxxx` (first 6 hex of sha256(personId)), and `memoryRead` returns the same opaque label as `personId`.
- Machine digests (`kind:'digest'`, see Consolidation) are written but not read back yet: like inner notes they are excluded from context, profile, search, read and recall of every stream.
- A capability cannot submit a proposal whose ID starts with `cons:`; that prefix marks the fact proposals Authority queues itself from a consolidation commit.
- `memoryEpoch` in context/search/read/recall/content is the stream's epoch: the entity epoch plus that stream's scoped-forget count (metadata key `streamEpochs`, no schema change).

Filtering happens in SQL before candidate limits/ranking. Local token overlap drives query relevance, then pin/importance and world-time decay; no vector service. Empty query uses a bounded recent candidate set. Same-entity private human memory stays person-scoped; shared views receive only explicitly authorized public material. Public DTOs exclude the private source quote. Learning capabilities cannot retrieve human private facts.

`eventAt` is an explicit owner-set integer timestamp or null; no model invents it. `recordedAt` is the source/record timestamp, not necessarily when the event happened. Date recall prefers explicit eventAt and clearly labels recordedAt fallback. No natural-language date extraction is claimed.

## Natural aging and important events

Default soft-retention half-life is 90 world days. Default conversational context downweights elapsed world time and lazily treats unpinned active items older than four half-lives as archived. Explicit memorySearch performs bounded deep retrieval including cold items; memoryRead by ID ignores natural age and marks archived items, and date-bounded memoryRecall can also recover cold important events. All three retain the same ACL/status/budget checks; hard-forgotten or superseded records remain unavailable. Natural archiving is not hard deletion. Paused world time does not age memories. Owner-controlled `importance` is 0..1; `pinned` bypasses the natural-archive cutoff. Public/retention changes affect only selected rows. No per-turn full-corpus model maintenance is required.

## Scoped content port (0.9)

POST `/v1/content` uses a capability credential and a bound `streamId` plus the current `memoryEpoch`. Authority derives entity/person/audience scope, rejects paused or retired requests, validates source observations for ingest/synthesis, delegates to a host-only content port, and rechecks scope before returning. Caller-selected entity/person/path or operator actions are not accepted. Media bytes are admitted only through the trusted transport client; the model-facing tool exposes opaque refs, bounded queries and URLs instead.

Actions are `ingest`, `transcribe`, `describe`, `synthesize`, `asset`, `attach`, `pending`, `search`, `fetch`, `jobResult`. `jobResult {ref}` returns the result of a finished background job (`{id,capability,title,status,failureCode,text,derived:true,isNewEvidence:false,isVerbatimUserText:false}`) only inside the conversation the job was registered in and only while Authority has handed its telling out (see Initiations). Registering a job (`jobStart`) is not an action of this route: only the operator route `/jobs/demo` sends it. The content port is not another personality or memory writer. It owns ephemeral files, derivatives and reply attachments; only the channel adapter can produce platform delivery receipts. `attach` queues a reply part, never records successful delivery. Search/fetch and vision results are external/derived data, not tool authority or new evidence.

Pure attachment observations carry optional `origin:'attachment'`, with a platform placeholder rather than fabricated authored text. Conversation memory proposals from that placeholder are rejected as `authored_text_required`; ASR/OCR/captions remain explicitly derived execution context, not verified human quotes. Existing text observations omit origin and retain their old canonical shape and behavior. Explicit authored confirmation can provide new ordinary evidence.

The product media store binds files to entity/person/stream/audience and original event IDs. Default cache retention is seven real days (physical cache retention, not personality/world-time decay). Explicit forgetting traverses file derivatives by original source events. The trusted purge stops content/SDK/QQ writers and removes selected media plus disposable speech scratch, preserving unrelated assets and the authorized synthetic voice reference. QQ/client/provider caches outside this store are not claimed erased.

## MEMORY_BATCH_V1: private maintenance role

Dedicated server grant `{role:'maintenance',entityId,hash}` is fixed to one entity. It cannot observe, submit ordinary proposals, select another entity, invoke admin APIs, or publish/forget content. Model never sees the token or gets tools.

- POST `/v1/maintenance/batch` / `client.maintenanceBatch({afterRevision?:0,limit?:8,mode:'private'|'public'})` -> `{entityId,taskId,memoryEpoch,cursor,items,personaText,world}`. At most 16 items, each bounded text and total source text <=6000 characters; persona <=1000. Items are already accepted fact/experience/note IDs, with type/text/importance/pinned/visibility/at. No raw observation dump, full private diary, generated reflection or entire state. Sensitive/forgotten sources are excluded. Public mode contains only explicitly public materials and no original private quotes. Paused or no eligible items means zero model work. Cursor may advance through skipped rows/diary-only changes with `items:[]`. If Core already saved the same task but Host lost its cursor save, the batch returns `items:[]`, the original cursor and `committedReceipt`; it must not trigger another model generation.
- POST `/v1/maintenance/diary` / `client.writeDiary({taskId?,kind,text,sourceIds})` validates a persisted server task's entity/mode/epoch/world revision and admitted memory IDs. Client can fill the most recently admitted task ID for that kind. It returns `{entityId,memoryEpoch,cursor,receipt:{id,status,revision},sourceIds}`. Same task/kind/content retry is idempotent; changed content conflicts. Host advances its cursor only after success. World pause rejects writes.

Private and public model inputs/calls are separate. With no public material there is no public model call. Private diaries are readable only by explicit admin listing; inner notes may be source material for the entity's private introspection, never conversational context. Public diary is an independent draft from admitted public items, not declassification of private diary prose. Publishing is an explicit owner action and does not send to QQ. Diary/reflection output never re-enters the source batch as a newly happened event.

## Consolidation: per-person digests (maintenance role)

Dialogue that has left a private conversation's replay window is read once and written back as long-term memory of that person. The worker only carries text: Authority picks the conversation, builds the input, validates the answer and writes. The same maintenance grant is used; a request can name no entity, stream or person. No schema change: the cursor and counters live under the metadata key `consolidation`, an admitted batch is a `maintenance_tasks` row (mode `consolidation`), a commit leaves a `diary_receipts` row (kind `consolidation`, a sha256 only).

- POST `/v1/maintenance/consolidation/next {}` / `client.consolidationNext()` -> `{entityId,task}` or `{entityId,task:null,reason:'idle'|'budget'|'paused'}`. `task` is `{taskId,trigger:'rollout'|'nightly',personaText,knownKeys,lastDigest,observations:[{ref,role,time,text}]}`: one private stream of one person, its observations after the cursor in order, each with a short ref (`o1`…), role `user|assistant` and Beijing minute. No observation, stream or person ID is returned. `knownKeys` (<=400 characters) are that person's active fact keys, `lastDigest` (<=300) the previous digest of that conversation, `personaText` <=1000.
  - Trigger `rollout`: the leading observations older than the stream's `windowFromAt`, minus a trailing line of the person (that line belongs to the first run still replayed, or was never answered), so a batch is whole completed runs. Trigger `nightly` (03:00–06:00 Beijing): the observations from before today, when there are at least 4 or one is older than 7 days; it also covers streams whose window is unknown.
  - Bounds: at most 4600 serialized characters and 100 observations a batch, 1500 characters an observation (cut with a marker). Forgotten observations, ones older than the backfill bound (14 days before the first `next` ever) and other roles are passed over; an observation matching the sensitive lexicon is sent as `[一条内容已省略]` and cannot be quoted. A batch in which the person said nothing readable moves the cursor without a task.
  - Budget per Beijing day: 2 batches a stream, 24 for the entity, counted when handed out (the same batch handed out again after a worker crash counts again). The stream with the fewest batches today is served first.
- POST `/v1/maintenance/consolidation/commit {taskId,outcome,digest?,facts?}` / `client.consolidationCommit`: `outcome:'ok'` with `digest:{summary,feeling?}` (<=300 / <=120 characters) and `facts:[{key,value,quote,ref}]` (<=4); `'invalid'` (the model's answer was unusable); `'deferred'` (the gateway's spend tier refused the call: the batch is uncounted, `deferredAt` is recorded, nothing moves). 409 when the task is gone, the world is paused or its revision changed, the stream's epoch changed or the cursor moved. One transaction:
  - An answer out of shape counts as `invalid`. Three invalid answers for the batch at one cursor skip it: the cursor moves, `skipped` is counted, audit `consolidation.skipped` (no text).
  - The digest is refused, while the cursor still moves, when it matches the sensitive lexicon (`sensitive`) or contains a note delimiter or 7 or more consecutive digits (`unsafe_text`). Otherwise it is stored as a `memory_items` row: collection `experiences`, `kind:'digest'`, private, that stream's person, importance 0.65, body `{summary,feeling?,derivedFrom:[observation IDs],fromAt,toAt,eventAt,capabilityId,streamId,taskId,via:'consolidation',scope:{kind:'person'}}`. It has no `evidence` and no `memory_sources` row, and it is never evidence for anything.
  - Each fact whose `ref` names a readable observation of the batch becomes an ordinary `fact.report` proposal in the inbox (ID `cons:<task prefix>:<n>`), reviewed by the same `review()` as any proposal: the cited observation is the provenance, confirmed human author, not sensitive; a quote that is not verbatim in that observation is accepted and marked `evidence.quoteVerbatim:false`, and the value need not occur in the quote. An accepted one gets importance 0.7 (0.8 for a fact proposed in the conversation) and is rejected with `newer_fact_kept` when the person has an active fact of the same key that is pinned or was recorded from words at least as recent. Other refs are dropped (`ref_unavailable`).
  - The cursor moves to the last observation of the batch, the batch's tasks are removed, audit `consolidation.committed` records opaque labels, IDs and counts. Returns `{status:'committed',digestId,digestRejected?,proposals,dropped}`; the same commit again returns `{status:'committed',digestId,replayed:true}`, a different one for the same task 409.
- Isolation: every batch is one stream; the digest and the facts take that stream's person from the binding, never from the model's answer. A digest cannot be made public.

## Initiations: a run she starts herself (conversation channels)

A turn in one person's private conversation when that person has sent nothing. Authority registers the request, the bridge of the channel it is for fetches it, runs it in that conversation's own queue and reports once. The caller of `next` can name no conversation, person or request: Authority picks. In this release the only source is the operator's poke and the only conversation a request may name is the owner's own private conversation: the one, on any conversation channel where an account of the owner is bound, in which the owner last spoke (by Authority's order of arrival; if never, the one bound last). A bridge is only handed, and can only report on, requests of its own channel (the capability of its credential) (the owner's newest `qq:<bot>:user:<owner>` binding); a stored request that names anything else is closed as `dropped:target`. No schema change: requests and the quiet hours live under the metadata key `initiations` (the newest 50 closed requests are kept).

- POST `/v1/initiations/next {}` / `client.initiationNext()` (any capability with policy `conversation.v1`; any other principal 403) -> `{initiation:{id,kind:'proactive',streamId,memoryEpoch,expiresAt}}` or `{initiation:null,reason:'idle'|'paused'|'busy'}`. At most one request is out per channel, and a request is handed out once: after that it is never returned again, whatever became of it.
- A waiting request is closed instead of handed out, with the reason as its outcome, and nothing is kept for later: `dropped:paused` (the world is paused, or was paused and resumed since the request was registered), `dropped:expired` (not fetched within 5 minutes), `dropped:target`, `dropped:epoch` (the conversation's memory epoch moved), `dropped:quiet_hours` (23:30–08:00 Beijing by default), `dropped:person_spoke` (the person has sent a message since).
- POST `/v1/initiations/ack {id,outcome}` / `client.initiationAck`: how a fetched request ended. `outcome`: `sent`, `partial` (some messages delivered, the rest not sent), `unknown` (a send without a platform receipt; never resent), `failed` (nothing sent), `declined` (she chose to say nothing), `deferred:budget` (the gateway's spend tier refused the run; `deferredAt` is recorded) or `dropped:<reason>` from the bridge's own checks (`target`, `expired`, `paused`, `epoch`, `stale`, `person_spoke`, `unsupported`). The same report again returns `{status:'recorded',replayed:true}`; a different one, or a report for a request that is not out, 409. A fetched request with no report within 20 minutes is closed as `unknown`; the bridge's own report may still replace that.
- The run itself: the bridge calls the executor with `input:{text,initiated:true}` and no evidence; the executor stores the text as an event block after a note saying nobody wrote (see ARCHITECTURE.md). Only messages with a platform receipt are observed, as `role:'assistant'`; no `user` observation exists for the run.
- Operator: POST `/initiative/poke {}` registers one request towards the owner (the body must be empty) -> `{id,kind,source:'poke',person,owner,status:'waiting'|'issued'|'closed',outcome,createdAt,issuedAt,endedAt,already?}`; while a request is open the same one is returned with `already:true`; a request that may not go out now comes back closed with the reason; 409 before the owner is bound. GET `/initiative/log` -> `{quietHours:{from,to,timezone,now},deferredAt,items:[...]}` newest first (opaque person labels and times, no text, no account). POST `/initiative/settings {quietHours:{from:'HH:MM',to:'HH:MM'}}` moves the quiet hours (equal ends: none); no console form uses it, scenario replay does.

### Completions: a background job finished

The content service runs background jobs (`capabilities/media/jobs.js`) and keeps each result until the person who asked has been told. It never calls Authority and never names who is told. On every `next` and `carry`, Authority asks it (control socket, `POST /jobs {action:'pending'}`, Authority's existing content-control credential) for the finished, untold jobs: `{id,capability,status,failureCode,scope:{entityId,streamId,personId,audience,memoryEpoch},source:{requestId,sourceEventId},endedAt,worldRevision,expiresAt,notice:'pending'|'carry'}`, never the result. What Authority decides goes back as `POST /jobs {action:'notice',id,state:'issued'|'carry'|'closed',outcome?}` before the caller is answered.

- Target rule of a completion (separate from the proactive rule, which stays owner-only): the conversation in the job record and nothing else. Checked against Authority's own tables each time: the stream is bound on exactly one conversation channel (the job is that channel's, and only that channel's bridge is handed it or told about it), private, with the job's person and entity; an account of that person is still bound on that channel; the stream's memory epoch is the job's; the observation that asked for the job (`source.sourceEventId`, when there is one) exists and is not forgotten. Otherwise the job is closed as `dropped:target`, `dropped:epoch` or `dropped:forgotten` and the content service deletes its result. The caller of `next` still names nothing.
- `next` may return `{initiation:{id,kind:'completion',streamId,memoryEpoch,expiresAt,jobRef}}`. A waiting proactive request goes first; at most one request is out at a time. The bridge reads the result with `/v1/content {action:'jobResult',ref:jobRef}` in that conversation's scope and runs an initiated turn about it.
- Told once: a job that was handed out is never handed out again while it is out, and never after `sent`, `partial`, `unknown`, `declined`, `carried` or a `dropped:target|epoch|forgotten`. Authority's own record forbids it, whatever the content service lists (that record is kept until the job's result expires, 7 days). After any other outcome (`deferred:budget`, `failed`, `dropped:person_spoke|paused|stale|expired|unsupported`) nothing reached her or the person: the job becomes carry-only.
- Carry-only instead of a turn of her own, decided at `next`: the world is paused or was paused since the job finished (`worldRevision` differs), the job finished 2 hours ago or more, or it is the quiet hours and the person has not written in the last 10 minutes.
- POST `/v1/initiations/carry {streamId}` / `client.initiationCarry` (any conversation capability, for its own conversations): asked by the bridge as an ordinary turn of that conversation begins. Returns `{initiation:{id,kind:'completion',streamId,memoryEpoch,expiresAt,jobRef,carried:true}}` for an untold job registered in that very conversation (pending or carry-only, same target rule), else `{initiation:null}`. The bridge attaches the result to the turn (`input.event`) and acks `carried` once the model has it; `carried` is accepted only for a request handed out this way. Another conversation's message never carries it.
- Operator: POST `/jobs/demo {seconds?:1..120}` registers the demonstration job in the owner's own private conversation (where the owner last spoke) (no other field; 409 before the owner is bound or while paused) -> `{id,capability,status:'queued'|'rejected',failureCode:null|'busy'|'daily_limit'}`. GET `/jobs` -> `{limits:{queued,perPerson},jobs:[{id,capability,title,action,priority,status,failureCode,attempts,progress,person,owner,createdAt,startedAt,endedAt,deadlineAt,notice:{state,outcome,at},result}]}` newest first, people as opaque labels. POST `/jobs/cancel {id}`. 503 without a content service.

## Operator API and forgetting

Separate operator socket/bearer; ordinary sources and maintenance workers have no owner credential. Existing `/world`, pause/persona/channel operations remain. `/world` includes `persona.default` (the code default); `/persona` accepts every persona field; `/persona/preview {patch}` is read-only and returns `{text,chars,limit}`. GET `/world` does not return private diary text or automatically invoke memory listing.

- GET `/entities`; POST `/entities {id,persona?}`.
- GET `/people` → `{people:[{personId,label,owner,actors,conversations}],limit,admitted,qq}` (people derived from actor bindings; `admitted` counts distinct people other than the owner; `qq` is the QQ worker's friend/queue status or null). POST `/people/attach {capabilityId,actorId,streamId,personId,move?}` says one account of a channel, with its private conversation, is the same human as a person already known (400 for an unknown person): the account and the conversation are bound to that person, so both channels share that person's memory while each keeps its own window. One that belongs to someone else is only moved with `move:true` (409 otherwise; the owner's is never moved; memory of the former person is not merged). Operator only: no capability route does this. `/world` `channels` lists every declared production channel and every registered conversation capability as `{id,name,status,enabled,boundStreams,expression?,friends?,receipts?}`. GET `/conversations` → bound streams with message count, last activity and stream epoch. GET `/spend` and the `/world` field `spend` proxy the model gateway's daily spend (null when unavailable); POST `/spend/settings {dailyCapYuan?,reducedPercent?,restrictedPercent?}` changes the cap/tiers.
- GET `/usage`, GET `/usage/history?days=1..90` (default 7) and POST `/usage/limits {limits:{capability:0..1000|null}}` proxy the model gateway's usage ledger the same way (503 when it is unavailable): today's row per capability, the finished days, and the daily limit of a capability that has one. Shapes: `model-gateway/README.md` "Usage ledger". Counts, units, time and money only; no text, no person.
- GET `/providers`, POST `/providers/key {provider,apiKey}` and POST `/providers/clear {provider}` proxy the model gateway's provider keys the same way (503 when it is unavailable): which providers hold a key, storing one, removing one. No response carries a key or a part of one, and Authority stores nothing. Shapes: `model-gateway/README.md` "Provider adapters".
- GET `/memory/status`; GET `/memory?entityId=...&limit=50&beforeRevision=...` explicitly lists selected entity memory and private/public diaries. Owner-only, never an automatic ordinary-chat read.
- POST `/memory/retention {entityId,id,importance?,pinned?,eventAt?}`.
- GET `/memory/consolidation?entityId=...` (read-only) -> `{entityId,day,timezone,calls,limits:{perDay,perStreamPerDay},since,lastIssuedAt,lastCommittedAt,deferredAt,paused:'spend'|'daily'|null,streams:[{stream,person,owner,behind:{observations,chars},waiting,calls,digests,skipped,lastAt}],extracted:{accepted,pending,rejected:{reason:count}},staleDigestIds}`. Opaque labels and counts only. `behind` is everything not consolidated yet (the live window included), `waiting` what has left the window. `staleDigestIds` are digests that still cover a forgotten observation (a release without the cascade forgot it).
- GET `/memory/sources?id=...&entityId=...` (read on request) -> `{entityId,id,machine,sources:[{id,role,at,text,forgotten}]}`: the observations one item was made from (a digest's `derivedFrom`, otherwise its evidence). Private evidence, never part of a listing. Listed items written by consolidation carry `source.machine`: `'digest'` or `'extracted'`.
- POST `/memory/public {entityId,id}` explicitly authorizes an eligible material; inner/appraisal/sensitive automatic publication is refused, and so is a machine digest.
- POST `/diary/private {entityId,text,sourceIds?}`, `/diary/draft {entityId,text,sourceIds}`, `/diary/publish {entityId,id}`.
- POST `/memory/forget-preview {entityId,ids}` returns memoryEpoch/revision, selected and expanded memory/diary/source IDs and affected streams. Owner may also select a raw observation ID, including rejected-sensitive evidence. Same-source memory derivatives are included, and so is every machine digest derived from an included observation (`digestIds` lists them; one way: a digest pulls in neither the other observations it covers nor their memories, and selecting only a digest removes only the digest). Derived multi-source diaries are removed without spreading deletion into their unrelated source memories. Selecting only a diary does not delete its original experiences.
- Forget scope (`epochScope` in preview, job and audit): a selection made only of person-private memory (and its sources) retires only the streams bound to those people plus the source streams — their stream epoch increases, the entity epoch and every other conversation stay. Public or person-less material, or a selection with no bound stream, still increments the entity epoch and retires every stream. Each `affectedStreams` entry of the job carries its new `memoryEpoch`; purge deletes that stream's earlier sessions.
- POST `/memory/forget {entityId,ids,expectedMemoryEpoch,expectedRevision?}` requires world paused and CAS. Erases selected source text/canonical data, related inbox body/canonical, memory rows/tokens, downstream diary/receipt content, legacy audit content and relationship evidence. Leaves only non-content audit/provenance/tombstones, increments the epoch of the affected streams (or the entity epoch, see forget scope), invalidates maintenance admission tasks (an open consolidation batch then commits with 409; a removed digest is not written again and the cursor stays), returns affectedStreams/sourceEvents and `{coreErased:true,externalCleanup:{status:'pending',id},complete:false}`.
- GET `/memory/cleanup/pending` returns explicit jobs. POST `/memory/cleanup/complete {id,memoryEpoch,report:{sdkPurged:true,localSourcesPurged:true,platform:'outside-control'}}` acknowledges trusted controlled SDK/source cleanup. Resume is refused while cleanup remains pending. ACK itself never resumes the world.

Core cannot erase a separately mounted SDK history, QQ local inbox or a platform/provider's remote logs. The trusted Host performs controlled external cleanup and reports it; stopping retrieval/compacting history is not physical erasure. Do not claim cross-system completion before the pending job is acknowledged, and never claim QQ/provider history/backups/SSD forensic remnants were erased by Core. SQLite secure deletion concerns the controlled live database, not external copies.

## Physical boundary

UDS/authentication is not a process sandbox. Authority DB/operator credentials and Docker/provider keys remain outside the model process boundary. Preserve the existing enforced runtime isolation; do not replace it with same-UID trust or unrestricted model filesystem/tools. No deployment, live migration or paid model validation is implied by local source tests.
